# Security, privacy and access control

## Roles

| Role | Workspace | Sees |
|---|---|---|
| Student | `/app` | Only their own profile, academics, alerts, plan, readiness, applications, notifications and conversations |
| Faculty | `/app` | Students in sections they teach, plus students an administrator explicitly shared with them (the same set in lists, direct access, analytics and their own report exports). Read-only on student records |
| Mentor | `/app` | Assigned mentees, and interventions for them. Read-only on student records |
| University administrator / HOD | `/app` | Everything in their own university; the only role that can edit a student record or download every report |
| Placement officer | `/app` | Student profiles, academics, skills, readiness, opportunities and applications for their university, plus aggregate risk statistics. **No** individual risk alerts, risk profiles or interventions, and read-only on student records |
| ACEDRA super administrator | `/platform` | Enquiries, tenants, team, audit. No student records without a grant |
| ACEDRA employee | `/platform` | As above, with configuration limited to assigned universities and only the permissions granted |

Navigation only reflects these rules. **They are enforced on the server**: role dependencies on every route,
the university guard on every tenant router, ORM-level tenant and student scoping, and resource ownership checks
(conversations, messages, interventions).

## Fixes made in this release (relative to v0.1)

| Issue in v0.1 | Fix |
|---|---|
| No tenant model; all data global | `TenantMixin` on 54 tables, ORM read scoping, write guard, per-tenant unique keys |
| Faculty and mentors could open any student by ID | Student scope enforced in the ORM and checked on every `student_id` path or query parameter (403 inside the tenant, 404 across tenants) |
| Password reset returned the reset token in the HTTP response | Emailed single-use hashed tokens; uniform responses |
| Default shared password (`StudentPass123!`) for created and imported students | Invitation-only activation; imports send invitations |
| Anonymous chatbot; conversations readable by session ID or by any admin | Auth required; strict per-user ownership; client session IDs ignored |
| Staff "personal mode" silently picked an arbitrary student | Staff must choose a student inside their scope |
| Hard-coded insecure JWT secret accepted in production | Production refuses to start with a default or short secret, wildcard CORS or SQLite |
| Tokens could not be revoked | `token_version` claim; logout, password, role and status changes revoke tokens |
| Upload type trusted the file extension | Magic-byte and UTF-8 checks, size limit, category and access validation |
| Tracebacks printed for every error | Structured JSON logging; generic 500 bodies; paths only (no query strings or bodies) in logs |
| Retrieval described as "semantic embeddings" | Labelled lexical retrieval; real embeddings only when configured |
| Deterministic fallback presented as AI output | `generation_mode` stored and shown; fallback is extractive or record-based only |
| `ACTIVE` alert filter matched nothing (assistant always reported zero alerts) | `ACTIVE` now means "not resolved or closed" |
| Personal assistant read a non-existent metric (0% attendance, "critical deficit") | Uses calculated attendance and the university's configured threshold |
| Students could apply to opportunities they weren't eligible for | Eligibility enforced server-side |
| Students saw staff intervention notes | Intervention detail is staff-only; the student list hides notes |

## Fixes made in the production-hardening pass

| Issue | Fix |
|---|---|
| Any staff role could download reports generated by an administrator (whole-university data) | Non-administrators list and download only their own reports (others return 404); their exports are built from their own student scope; report types are limited by role |
| Faculty, mentors and placement officers could edit student status, term, section and mentor | Only administrators edit student records; students edit only their own contact details; the mentor id is validated |
| Placement officers could read individual risk alerts and interventions | 403 on `/risk/alerts`, `/risk/alerts/{id}`, `/risk/students/{id}` and `/interventions` |
| No sign-in lockout; response time revealed which emails exist | Lock after `LOGIN_MAX_FAILED_ATTEMPTS` consecutive failures for `LOGIN_LOCKOUT_MINUTES` (a password reset unlocks); unknown emails cost the same bcrypt check |
| Refresh tokens were reusable for 7 days and unlimited | Single use, recorded by hashed id; presenting a used token ends every session for the account; `/auth/refresh` is rate limited |
| Older password-reset links stayed valid | Issuing, using or changing a password invalidates all other reset links |
| Audit records trusted a caller-supplied `X-Forwarded-For` | The header is never read by the application; the server trusts only the bundled proxy, which overwrites it |
| Rate limits were per process and, behind Nginx, shared by all visitors | Counters live in Redis in production and are keyed by the real visitor address |
| A changed role left no faculty or mentor profile (empty student scope) | The missing profile is created with the role change |
| Duplicate identifiers and nulls returned HTTP 500 | 409 for constraint conflicts; invitations are validated before an account or email exists |
| Emails were sent inside the request before commit (dead links after a rollback; slow relay blocked requests) | Outbox: queued in the transaction, delivered after commit, retried with back-off |
| CSV exports could carry spreadsheet formulas | Cells starting with `=`, `+`, `-`, `@` are prefixed with a quote |
| Inline script allowed by the CSP; no TLS in the stack | Theme bootstrap moved to a file and `script-src 'self'` only; Nginx terminates TLS and redirects HTTP |
| The built-in development secret was accepted whenever `ENVIRONMENT` was not `production` | Unknown `ENVIRONMENT` values are rejected, the built-in secret is refused with any database server, and the production image defaults to `ENVIRONMENT=production` |

Lockout is a trade-off: someone who knows an email address can keep that account locked by failing sign-ins.
The lock is short, is recorded in the audit log (`LOGIN_BLOCKED`), and the account owner can always get back in
with a password reset.

## Release-candidate controls (v1.0.0-rc.1)

| Area | Control |
|---|---|
| Production configuration | The API validates its settings before migrating or serving and refuses development values: built-in or weak `SECRET_KEY`, SQLite or a development database password, wildcard or `localhost` origins, a non-HTTPS public URL, `EMAIL_PROVIDER=log`, the built-in sender address, `SEED_DEMO_DATA=true`, `ALLOW_INSECURE_DEV_SECRET=true`. The container entrypoint runs the same check first, so a bad configuration never reaches the database |
| Sample data | `database/seeds/seed_all.py` exits with an error when `ENVIRONMENT=production`; the demonstration passwords cannot be loaded into a live system |
| API surface | `/docs`, `/redoc` and the OpenAPI schema are not served in production. Email bodies (which hold single-use links) are hidden in the platform outbox in production |
| Dependencies | Python packages are pinned exactly; `pip-audit` and `npm audit` run in CI and report no known vulnerabilities at this release (React Router 6 → 7 and Vite 5 → 7 removed the advisories that were open) |
| Secrets | detect-secrets checks the working tree against a reviewed baseline, and `scripts/scan_git_history.py` and gitleaks check every commit, on each push. The history contains no credentials: only development placeholders |
| Backups | Dumps are owner-readable only, checksummed and verified on write; restores verify the archive, refuse a non-empty target and are transactional |

## Other controls

* bcrypt (12 rounds) password hashing; password policy of at least 10 characters mixing three character classes.
* Rate limits: login, token refresh, invitation and reset 20/min, public enquiries and contact messages 5/hour,
  everything else 240/min (slowapi with a Redis store in production; disabled in tests). The enquiry and contact forms have honeypot fields; the contact form also
  rejects free-mail addresses and link-heavy messages.
* Legal documents: only ACEDRA super administrators can create, edit, approve and publish versions; ACEDRA
  employees can read them; university accounts get 404. Publishing requires a recorded approval, published
  versions are immutable, and all actions are audited. Acceptances are recorded per user, university, document and
  version; signing in is never treated as acceptance. `LEGAL_ACCEPTANCE_ENFORCED=true` makes the API refuse
  workspace requests (428) until the current versions are accepted.
* The frontend loads no third-party scripts, fonts or trackers and sets no cookies; the Nginx CSP allows only
  `'self'` origins.
* CORS restricted to configured origins and methods. Security headers set by both the API and Nginx; the Nginx
  CSP restricts `connect-src` to self.
* Prompt-injection patterns are blocked in questions and neutralised inside retrieved documents. The system
  prompt forbids following instructions found in documents or discussing other students.
* Audit log entries are tenant-scoped for university administrators and platform-wide for ACEDRA staff, covering
  sign-in success and failure, invitations, configuration, grants, every student-data access and enquiry changes.

## Tests that attack these controls

`documentation/RELEASE_VERIFICATION.md` records the live checks run for this release candidate (37 against a
production-mode API on an empty PostgreSQL database, 46 for tenant isolation, roles and authentication against a
seeded one); the scripts are in `scripts/verification/`.

`backend/tests/test_production_hardening.py` covers every row of the hardening table above that lives in the
backend. `backend/tests/test_multitenancy_and_roles.py` and `test_platform_workflow.py` cover:
cross-tenant reads and writes by ID, tenant-isolated retrieval, disabled modules, students calling admin and
platform endpoints, university admins calling platform endpoints and assigning platform roles, faculty and mentor
scope, platform accounts reading student data, conversation ownership, the explicit grant flow with audit and
revocation, the password reset and logout revocation, expired and forged tokens, role-change escalation and the
whole enquiry → activation workflow.
